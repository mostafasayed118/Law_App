## 1. Scope

Client-only wiring that turns the current `Session.memberships = []` honest
placeholder into real hydrated data, and the active-org context from an
in-memory store into a persisted, restored one:

1. **Membership hydration** — new `MembershipRepository` (domain seam) +
   `SupabaseMembershipRepository` (data) reading the RLS-scoped
   `memberships`/`organizations` SELECT surface; `AuthCubit` hydrates
   `Session.memberships` after sign-in / restore / demo success.
2. **Active-org persistence** — `ActiveOrgStore` (Phase 7 slice 7.0, D-M7/D-08)
   gains a SharedPreferences-backed persistence seam (the LocaleStore
   pattern), so the selected org survives restarts; still client-side UX
   context only, never an authorization claim.

## 3. State shape & data flow

- **No new Cubit/state class.** D-P32.2: extend the shipped `ActiveOrgStore`
  (app-scoped ChangeNotifier) with persistence instead of introducing a
  parallel `ActiveOrgCubit` — avoids an org-hub migration with no
  behavioral gain. API unchanged (`activeOrganizationId`, `syncFromSession`,
  `select`) plus a persistence side-effect.
- **Flow:** sign-in/restore success (memberships `[]`) → `AuthCubit` emits
  `ViewLoading` → `MembershipRepository.loadMemberships(userId)` →
  `SupabaseOrgApi.listMyMemberships()` (PostgREST SELECT, RLS) → mapper
  (existing `userRoleFromServerName`/`membershipStatusFromServerName`; null
  org-name tolerated; unknown-role row dropped) → `Session` rebuilt with
  hydrated memberships → emitted → `ActiveOrgStore.syncFromSession`
  (seed-guard keyed on userId: same user does not re-seed, so a selection
  survives) → org hub renders; `select(org)` persists.
- Expiry honored **before** hydration (`sessionExpired` → reauth, never
  hydrates — AC-3). Provider-empty stays the honest `[]` (plan §6).

## 4. Assumptions & non-goals

- **No server changes, no new RPCs, no matrix addendum** — consumes the
  applied P2 SELECT surface (`memberships` own-row policy, `organizations`
  active-member policy) exactly as rehearsed/applied.
- **Name-resolution note (plan §6):** `organizations` SELECT is
  active-member-only, so `organizationName` resolves for active memberships;
  a suspended/removed membership's own row is visible but its org row is not
  → the mapper tolerates a null name for non-active memberships.
- **Unknown schema role → no capability projection (D-T5, D-P32.1):** a
  server role outside the six-value enum is dropped (loud via debug), never
  silently projected.
- Non-goals: P3.3 org-management screens, invite acceptance (P3.4), owner
  admin (P3.5), the §4.5 provider loop (D-45.1 ratified plan stands).
