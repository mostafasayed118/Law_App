## Findings (from the device, not from the report)

1. **The posture gate covers 7 of 13 local-only notes.** `c835ced` gates the notes on
   tasks / matters / matter details / vault / messages / thread detail / invoices /
   notifications via `backendIsLocalOnly`. The remaining surfaces still render demo
   copy **unconditionally** in a configured, real-backend build:
   `home_entry_cards` subtitles ("Schedule a consultation — development demo.",
   "Browse demo matter files — development demo."), the Settings role card
   ("Partner / Development-only demo session"), the sign-out button label
   ("End demo session"), plus `discovery`, `approvals`, `compliance`, `research`,
   `video` surfaces (`localOnlyNote:` passed unconditionally in their builders).
   Observed live in the configured build against the real backend.

2. **Warm deep links land on the raw URI ⇒ "Page Not Found".** Sending
   `am start -a android.intent.action.VIEW -d "com.legalhub.app.dev:///tasks"`
   while the app is running navigates to the *whole URI*:
   `GoException: no routes for location: com.legalhub.app.dev:///tasks`
   (`Page Not Found` screen). Cold starts sometimes work, sometimes not — flaky.
   The `app_links` wiring pushes the URI instead of its path.

3. **A membership created in-session is not picked up.** After creating the org,
   the org hub still rendered the "Create Organization" form and
   **"Create matter"** said *"No active organization is selected. Choose an
   organization from the org hub, then return here to create a matter."*
   The membership row exists and is `active` (PostgREST-verified) ⇒ the session
   never activated it, and the hub exposes no "select active org" action.
   Consequence: a brand-new real user cannot reach the documents / messages /
   invoices surfaces (their home entries need partner capabilities).

The **eighth** surface (message thread detail) is **not reachable** with the current
client surface: `message_threads` has no INSERT grant for `authenticated`
(`revoke all … from anon, authenticated` in `migrations/06_message_threads.sql`) and
no create-thread RPC exists — the app only reads threads and calls
`send_message(p_thread_id, p_body)` on an existing one. A manual insert attempt was
rejected by Postgres (`42501 permission denied for table message_threads`), so a
real user cannot start a conversation from the app at all (new finding 5).

### Root cause refined (finding 3)

The membership **is** hydrated — but only on the **restore (cold start)** path, not on
the sign-in path. Sequence reproduced on the device:

1. sign in → **Create Organization** → org created, membership row `partner/active`;
2. sign out → sign in → org hub **still shows the "Create Organization" form**;
   "Create matter" says *"No active organization is selected."*;
3. force-stop + relaunch (restore path) → org hub **shows "QA Device Firm" /
   qa-device-131043@legalhub.test / Partner / ACTIVE** → matter creation works.

So: a user who creates an organization has to restart the app before the
organization becomes visible and usable.

### New finding 4 — a created matter is invisible to its creator

`create_matter` defaults both assignees to `None`, and the read policy
(`policies/matters.sql`) is

```
using (public.is_active_member(organization_id)
       and (assigned_client_id = auth.uid() or assigned_attorney_id = auth.uid()))
```

⇒ a partner who creates a matter without assigning someone gets a matter they can
never read back. The create screen acknowledges it ("It appears on your matters
list only when your access allows reading it"), but the default is the dead end.
Observed: the first matter (no assignee) stayed invisible; the second one, with the
client assigned to the QA user, appeared (and was visible over PostgREST, RLS
included). Side note: the matters list does not refresh on return from the create
screen — it only updates when the screen is re-entered.
